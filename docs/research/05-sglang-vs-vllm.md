# vLLM vs SGLang for GLM-5.3-Flash and DeepSeek-V4-Flash on 2× DGX Spark (GB10) — September 2026 state

Conventions: **[F]** = fact with a source; **[I]** = my inference from the facts. All numbers are quoted as reported by the source; "c1/c4" = concurrency. Sources are listed at the end.

---

## 1. Engine architecture comparison (2026)

### vLLM V1

**Scheduler.** [F] The V1 scheduler schedules RUNNING requests first, then WAITING; the per-step budget is `max_num_batched_tokens`; admission is gated by `max_num_seqs` (`if num_running >= self.max_num_running_reqs: break`); speculative slots are charged against the budget (`input_budget -= num_new_tokens + draft_slots`). The only anti-starvation knob is `long_prefill_token_threshold`: `if 0 < long_prefill_token_threshold < num_new_tokens: num_new_tokens = long_prefill_token_threshold` (per-step cap on a long prompt's chunk). [F] `max_num_partial_prefills` / `max_long_partial_prefills` do **not** exist in V1 — engine start fails with "Concurrent Partial Prefill is not supported" (issue #39737, still open). Default `long_prefill_token_threshold` is 0 = disabled, so by default one long prompt monopolises `min(remaining, token_budget)` every step until done ([vllm scheduler.py], [MiaAI issue #110]).

**MoE backends.** [F] `MoEBackend` in `vllm/config/kernel.py` enumerates: `auto, triton, batched_triton, deep_gemm, deep_gemm_mega_moe, cutlass, flashinfer_trtllm, flashinfer_cutlass, flashinfer_cutedsl (FP4 only), flashinfer_b12x ("FlashInfer CuteDSL fused MoE for SM12x"), b12x ("b12x FP4 MoE kernels on SM12x"), flashinfer_moe_ep_mega_deep_gemm, flashinfer_moe_ep_mega_cutedsl, marlin, humming, triton_unfused, aiter, hpc, emulation`. The modular-kernel doc distinguishes "standard" activation-format experts (Triton, CUTLASS FP4/FP8, FlashInfer, TRTLLM, Marlin, DeepGEMM) from "batched" format experts (batched Triton/DeepGEMM/CUTLASS/Marlin) used with DeepEP-LL style all2all. [F] On SM_121 the FP8/MXFP8 oracle rejects `FLASHINFER_TRTLLM` because `_supports_current_device()` requires `is_device_capability_family(100)`; MXFP8 MoE then drops to Marlin W8A16 (issue #43906). [F] Community GB10 guides say NVFP4 MoE must run `--moe-backend marlin` (CUTLASS FP4 GEMM crashes on sm120/121) — with NVFP4 weights dequantised to BF16 before GEMM ([vlaicu playbook], [ai-muninn]). NVIDIA later clarified GB10 *does* have NVFP4 tensor cores but needs the `sm_121a` target ([ai-muninn]); the `b12x`/`flashinfer_b12x` backends are the upstream response, but none of the GB10 GLM recipes I found use them yet.

**Attention.** [F] GLM-5.3-Flash uses NoPE sparse MLA (`qk_rope_head_dim=0`, `kv_lora_rank=512`, `index_topk=2048`, kpool=4); on sm_121 it required an "extended sparse-attention backend" over FlashInfer 0.6.18 because the stock image's MLA backends hard-wire rope dims ([tonyd2wild TP2 thread], [4×Spark thread]). The DSA top-k indexer wants 128 KB SMEM / 62 CTAs at 512K vs GB10's ~99–101 KB, so persistent_topk/cooperative-workspace paths had to be disabled for CC 12.x. [F] FlashInfer's SM12x NVFP4-KV kernels are dense-MHA only, not sparse MLA; there is no BF16-KV sparse-MLA kernel for GB10 in the EXL3 lane, hence fp8 `fp8_ds_mla` is mandatory there ([MiaAI README]).

**Hybrid state.** [F] vLLM uses one unified block pool. For attention+Mamba/KDA hybrids it grows `block_size` until `block_size × kv_hidden_attention ≥ state_size_mamba` and pads the state to one page; the doc admits this "can result in more than 400 block_size … too large" ([hybrid KV cache manager]). In practice GLM-5.3-Flash lands on `--block-size 2304` ("load-bearing") and the EXL3 lane reports a 3584-token "MLA hybrid page". [F] `--mamba-cache-mode {align, all, none}` (align = snapshot the recurrent state only at scheduler-step ends that fall on `i × block_size`; default with prefix caching; "the only mode the KDA backend supports"), `--prefix-match-unit N` lets hash keys land inside a physical block (e.g. 16 vs a 1024-token hybrid block), and `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` sparsifies state snapshots (at block 128 the snapshots consumed ~80% of KV blocks; hit rate fell 85%→75%; with interval 512 it recovered to 98.5%) ([PR #45845], [LMCache Kimi-Linear], [PR #46384 search]). `--mamba-cache-dtype` / `--mamba-ssm-cache-dtype` (`float32|float16|bfloat16`) control state precision ([cache.py]).

**Speculative decoding.** [F] `SpeculativeConfig.method` ∈ {ngram, ngram_gpu, medusa, mlp_speculator, draft_model, suffix, eagle, eagle3, mtp variants (deepseek_mtp, qwen3_next_mtp, …), dflash, dspark, custom_class, extract_hidden_states}. DFlash/DSpark auto-enable `parallel_drafting`; `draft_tensor_parallel_size` must be 1 or = target TP; the drafter can have its own `moe_backend`, `attention_backend` (DFlash needs non-causal), `kv_cache_dtype`; `num_speculative_tokens_per_batch_size` is a `(range_start, range_end, k)` schedule to taper k with batch size; `enable_adaptive_verification` exists for DSpark only ([speculative.py]). [F] DFlash landed in PR #38300 (merged 2026-04-15, `vllm>=0.20.0`) with the explicit initial limitations "no chunked prefill, prefix caching, hybrid models, or CUDA graphs". [F] DFlash2 landed in PR #52816 (merged 2026-08-21) and runs only on the V2 model runner; Qwen3.8-27B on H200: c1 224.6 tok/s (3.51×), c32 2,759 tok/s (2.20×), conv+selector cost 0.84% of latency at batch 1.

### SGLang

**Scheduler / RadixAttention.** [F] Default policy is "prefill first, decode second"; maintainers' knobs for decode-friendliness are `--schedule-conservativeness ~0.8`, `--max-prefill-tokens 2048`, `--chunked-prefill-size`, `--enable-mixed-chunk`, and capping `--max-running-requests` at 12–16 ([discussion #27762]). `--chunked-prefill-size -1` disables chunking; `--max-prefill-tokens` default 16384; `--schedule-policy {lpm, fcfs, dfs-weight, lof, priority, routing-key}`; `--page-size` default 1 ([server args]). [F] Since v0.5.16 `UnifiedRadixTree` is the default radix cache for SWA, Mamba and DSA models; HiCache for hybrid models is default since v0.5.15 ([releases]).

**MoE.** [F] `--moe-runner-backend` ∈ {triton, cutlass, flashinfer_cutlass, flashinfer_trtllm, flashinfer_trtllm_routed, deep_gemm, megamoe (W4A8/W4A4 via MegaMoE)} plus `--moe-a2a-backend` (DeepEP etc.), `--ep-size`, `--enable-dp-attention --dp-size` ([GLM-5.3-Flash cookbook], [EP docs]). [F] v0.5.13 added a "GB10 FP8 fused MoE Triton config"; v0.5.16 moved SM120 to JIT for CUTLASS FP8 blockwise ([releases]).

**Hybrid state.** [F] Two physically separate pools: a **Mamba pool allocated per request** and a **KV pool allocated per token**, sized by `--mamba-full-memory-ratio` / `--max-mamba-cache-size` (more Mamba slots ⇒ fewer KV tokens); `HybridReqToTokenPool` binds state lifetime to request lifetime; `MambaRadixCache` stores state checkpoints in the tree with a separate LRU. Speculative decoding gives **one Mamba slot per draft token**, promoting the accepted slot; PD-disaggregation transfers the Mamba state atomically ([PyTorch/SGLang hybrid blog]). [F] Linear-attention kernels: KDA CuteDSL prefill on Blackwell "1.08–1.52× faster than Triton" (v0.5.14); `recurrent_kda` decode 29.6 µs on SM100 (v0.5.16) ([releases]).

**Speculative decoding.** [F] Algorithms: EAGLE/EAGLE3, NEXTN (MTP; "FROZEN_KV_MTP runs as MTP mode"), STANDALONE, NGRAM, DFLASH, DSPARK; flags `--speculative-num-steps/--speculative-eagle-topk/--speculative-num-draft-tokens/--speculative-adaptive/--speculative-draft-attention-backend`. DFLASH forbids `--enable-dp-attention`, requires `pp_size==1`, and **disables the overlap scheduler**; NGRAM also disables mixed chunked prefill; overlap scheduler V2 only supports `topk 1` ([SGLang spec docs]). [F] DFlash2 merged in SGLang PR #35371 (2026-08-19; Qwen3.8-27B GSM8K c1 236.1 tok/s 3.43×, c32 1,922 tok/s 1.45×); GLM-5.3-Flash DFLASH via PR #36708 (merged 2026-08-27) which contracts mHC states (`hc_mult×hidden`→`hidden`) for the drafter; v0.5.16 fixed "silent KV corruption when speculative draft tokens exceed 4" and budgets the DFLASH draft KV pool from its own attention geometry ([releases]). [F] GLM-5.3-Flash base support is PR #36507 (still open with CI failures; verified on 4×GB300 and 8×H100) and ships as `lmsysorg/sglang:glm-5.3-flash-arm64`.

[I] On GB10 the ranking is set by the expert GEMM path, not by the scheduler: FP8 block-scaled weights hit native FP8 tensor cores (DeepGEMM/CUTLASS SM120 JIT, or Triton w8a8) ≫ NVFP4 through FlashInfer-CUTLASS ≈ EXL3 fused ≫ Marlin dequant. GLM-5.3-Flash's 288×2048-wide experts at top-8 mean an 8K chunk spreads ~230 tokens per expert on average (skewed), so grouped-GEMM tile utilisation and padding dominate; Marlin (decode-oriented W4A16) and the original EXL3 path (also decode-tuned) suffer most, which is why MiaAI had to write a separate "fat-expert" prefill kernel for +20%. SGLang and vLLM with the *same* FlashInfer-CUTLASS NVFP4 kernel land in the same ~1–2k band; SGLang's extra edge at 8K in your measurements is consistent with its larger default prefill batch (`max-prefill-tokens` 16384 vs vLLM's `max-num-batched-tokens` 7168 in the MiaAI recipe) and no chunk-cap interleaving, not with a fundamentally better MoE runner. Neither engine has an sm_121 DeepGEMM path for GLM's NVFP4 experts today.

## 2. GLM-5.3-Flash on each engine

**Model facts.** [F] `Glm5NextForConditionalGeneration`, 45 layers, hidden 4096, 288 routed experts + 1 shared, top-8, MoE intermediate 2048, first 3 dense; 64 KDA heads × 128; every 4th layer DeepSeek-style sparse attention (index_topk 2048, kpool 4), MLA kv_lora_rank 512 / NoPE head 256 / rope 0; 1 NextN (MTP) layer; hc_mult 4; FP8 e4m3 checkpoint; 1,048,576 positions ([config.json]). 320B total / 18B active ([model card]).

**Official recipes.** [F] vLLM: `vllm serve zai-org/GLM-5.3-Flash --tensor-parallel-size 4 --kv-cache-dtype fp8 --speculative-config '{"method":"mtp","num_speculative_tokens":5}'` with `--tool-call-parser glm47 --reasoning-parser glm45`; FP8 ~306 GiB, NVFP4 variant needs Blackwell; sparse-MLA init needs FlashInfer ≥0.6.18 ([recipes.vllm.ai]). Dynamo/vLLM H200 targets use MTP7 + DeepGEMM + `FLASHMLA_SPARSE`, prefix caching with match unit 128; disagg needs `VLLM_SSM_CONV_STATE_LAYOUT=DS` and `VLLM_KV_CACHE_LAYOUT=HND` ([Dynamo recipe]). SGLang cookbook: BF16/FP8, W4A8/W4A4 MegaMoE, adaptive MTP "5/1/6" (`--speculative-num-steps 5 --speculative-eagle-topk 1 --speculative-num-draft-tokens 6 --speculative-adaptive`), FP8-KV pairs with TRT-LLM DSA, BF16-KV with TileLang DSA; GB300 4-GPU: TTFT 598 ms / TPOT 6.43 ms / 2,281 tok/s/GPU at c16; FP8-KV+TRT-LLM DSA is 2.9–5.7% faster with a 1.8× larger pool and a 0.15-pt GSM8K gap ([SGLang cookbook]).

**Quant formats on GB10.** [F] FP8 native only fits at TP4 (78 GiB/rank) ([4×Spark thread]); NVFP4 (LibertAIDAI 181 GiB, RedHatAI compressed-tensors recommended over ModelOpt due to "intermittent corrupted token IDs") and EXL3 4bpw (176 GB) fit TP2. KLD vs teacher: TR3 6bpw 0.0137, official FP8 0.0206, EXL3 4bpw 0.0246, NVFP4 0.0605 ([MiaAI README]). No AWQ/GPTQ GB10 recipe found.

## 3. DeepSeek-V4-Flash on DGX Spark

[F] Architecture: 43 layers, hidden 4096, 256 routed experts + 1 shared, top-6, intermediate 2048; MLA with 64 heads, head dim 512, rope 64, q/o LoRA 1024; compressed sparse attention `index_topk 512`, compression ratios alternating (0, 0, 4, 128 …); 1 MTP layer; hc_mult 4; FP8 e4m3 weights, block [128,128], `ue8m0` scales; YaRN ×16 to 1M ([config.json]); 284B/13B active; the card says experts are FP4 and the rest FP8 ([model card]).

[F] Recipes: `jasl/vllm` (PR #41834 "SM12x support for DeepSeek V4 Flash", open, needs rebase as of 2026-08-13) built on `eugr/spark-vllm-docker`; image `hazyumps/deepseek-v4-flash-gb10:sm121-cu130-20260727d` (tag `sm120-pr-41834-stable-preview-20260727d`); TP=2 + EP; `sm12x_deep_gemm_fallbacks.py` bind-mounted over the attention-ops module; FlashInfer sparse-MLA prefill/decode with FlashMLA/Triton fallback; fp8 KV block 128; NCCL 2.30.4 via `LD_PRELOAD` (2.28.9 wedges TP after ~30 s: "shm_broadcast: No available shared memory broadcast block"); `FULL_AND_PIECEWISE` cudagraphs; `--max-num-seqs 4`; persistent `/root/.cache/vllm` and `/root/.triton/cache` mounts are mandatory; `--no-ray` / `--distributed-executor-backend mp`. Spec: DSpark `{"method":"dspark","num_speculative_tokens":5}` (k must be a multiple of the 5-token block; `draft_sample_method` probabilistic under concurrency, greedy garbles cold), 3 draft groups + Markov head; MTP-2 is the fallback (acceptance 0.69–0.77). Numbers: prefill 1.6–1.8k tok/s (hazyumps, 384K ctx), 2,639 tok/s @100K (tonyd2wild 1M/NVFP4-KV lane), decode 47–60 easy / ~40 mixed (hazyumps), 84.3 peak / 62 code / 31–37 prose / ~22 per stream at 4 concurrent (tonyd2wild), 38.4 c1 → 144.6 aggregate c16 on official FP8 (r0b0tlab), 4× Spark TP4: 49.4 c1, 179.9 agg at n=8. Kernel state: DeepGEMM #324 added sm120 kernels (merged 2026-06-24 into `nv_dev`); the SM12x tracker (#41063) lists native `sm120_fp8_einsum`, `sm120_fp8_paged_mqa_logits`, `sm120_tf32_hc_prenorm_gemm` and open gaps for FP4 GEMM/attention/einsum (`sm100_fp8_fp4_gemm_1d1d` emits tcgen05 ISA that GB10 rejects).

[I] Why this lane prefills 1.5–2.5× faster than your GLM lanes: (1) 13B vs 18B active and top-6 vs top-8 over the same 2048-wide experts → ~30% fewer expert FLOPs per token; (2) the FP8 block-scaled expert GEMMs run on native FP8 tensor cores through DeepGEMM-SM120/CUTLASS-JIT/Triton w8a8 paths, whereas the GLM lanes either dequantise (Marlin, EXL3 trellis → fused custom kernel) or go through FlashInfer-CUTLASS NVFP4 with immature SM12x tuning; (3) DeepSeek's CSA/HCA attention with `index_topk 512` plus 4×/128× compression is cheaper per token than GLM's DSA `index_topk 2048` with kpool, and it has no KDA chunked-scan pass on 34 of 45 layers; (4) the DeepSeek sparse-MLA path has had months more sm_121 kernel work (PR #41834 since spring) than GLM-5.3-Flash (released 2026-08-26). Note the DSpark drafter itself has MoE FFNs (256 experts, top-6) in 3 layers, so its prefill isn't free either.

## 4. Speculative decoding for prefill-heavy agentic workloads

**Drafter prefill cost.** [F] DFlash does not run an independent prefill: target hidden features from 5 uniformly-sampled layers are extracted during the target's prefill and injected into the drafter's KV cache of every layer via a fusion projection; "drafting cost no longer scales with the number of generated tokens" ([DFlash paper]). vLLM's `dflash.py` implements exactly this: `precompute_and_store_context_kv()` "pre-inserts context KVs directly into cache", with separate context/query buffers so CUDA graphs keep stable addresses, and the context path is incremental (works with chunked prefill) ([dflash.py]). [I] So DFlash/DFlash2's prefill overhead ≈ one linear projection per prompt token — negligible vs the target's 45 layers. EAGLE-3 and MTP drafters, by contrast, are real transformer layers (GLM's NextN layer carries attention + MoE) that must run over every prompt token with their own KV — ~1/46 of target compute plus a second attention pass; in SGLang the doc explicitly warns "draft prefill affects GPU memory usage significantly" and both engines charge draft tokens against the step budget (vLLM: `input_budget -= num_new_tokens + draft_slots`). [F] The real prefill-side costs of DFlash2 you should budget: drafter KV (2,048 B/token, 5 SWA layers → ~0.6–0.7 GB waste at 1M from page misalignment, #108), KV-pool shrinkage (581K vs 965K tokens at 262K in the marlin lane), and the loss of SGLang's overlap scheduler under DFLASH.

**Acceptance on GLM-5.3-Flash.** [F] MTP-4: ~0.55 per-position average (tonyd2wild); content-driven "0.70+ on structured/code, ~0.33 on freeform prose". DFlash2 k=7: 74.1% (420/567 drafted) on code; MiaAI per-position 0.98/0.98/0.94/0.94/0.91/0.83/0.83 structured (6.71 tokens/step) vs 0.75/0.58/0.41/0.28/0.16/0.09/0.06 prose (2.39/step); SGLang "~5–6 of 6-token blocks on code"; GB300 54–67%. For Qwen3.8-27B the Inco blog reports mean acceptance MTP 4.28 vs DFlash2 4.80 (GSM8K 5.02 vs 5.46) — so DFlash2's win on GLM is mostly k=7 blocks vs k=4 MTP plus a non-degrading tail, not a dramatically higher per-position rate ([Inco blog], [PR #35371]).

**Batch-size crossover.** [F] DFlash (SGLang, Qwen3-4B): 4.8× at c1 → 4.3× c4 → 4.1× c8 → 3.5× c16 → 2.9× c32; LLaMA-3.1-8B only 1.4–1.8× at c32 ([DFlash paper]). DFlash2: 3.43×→1.45× (SGLang) and 3.51×→2.20× (vLLM) from c1→c32 on H200. On **2× GB10** the crossover is far earlier: SGLang DFlash2 vs no-spec aggregate = c1 37.3/14.5, c2 49.5/27.1, c4 51.7/36.8, **c8 47.3/55.1, c12 48.8/55.0** — spec decode loses beyond ~c6 ([beastllama forum]). MiaAI's vLLM lane still scales at ×4 (146.5 agg) but per-stream falls 62.9→37.1. [I] Reason: per step the target must stream ~9–10 GB of 4-bit expert weights across the two Sparks (~18–20 ms floor at 273 GB/s/node ≈ 50–55 tok/s per sequence ceiling) *and* read KV for every sequence; with k=7 the verify batch is 8×c tokens, so at c=8 you already verify 64 tokens/step and touch far more experts (top-8 × 64 tokens ≈ most of 288), erasing the bandwidth amortisation that makes speculation pay. [F] Mitigations exist: vLLM `num_speculative_tokens_per_batch_size` (batch-indexed k schedule), SGLang `--speculative-adaptive`, DSpark's `enable_adaptive_verification` (vLLM) / confidence-scheduled blocks (SGLang v0.5.16, "383.7 tok/s at accept length ~5" on V4-Pro). The old V0 `--speculative-disable-by-batch-size` does not appear in the V1 `SpeculativeConfig` field list [I].

## 5. Concurrency and memory on hybrid models

**vLLM.** [F] One unified pool; KDA state padded to the attention page, which forces `block_size` up to 2304–3584 tokens on GLM-5.3-Flash; per-request state cost is therefore one page per KDA group plus (with prefix caching in `align` mode) one snapshot per block boundary the request crosses — the snapshot flood is why `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` exists. [I] Raw KDA state is small (34 layers × 64 heads × 128×128 × 2 B ≈ 71 MB per request in bf16, halved per rank at TP2), so the state pool is **not** what limits you at 1M; the MLA KV is (~11 sparse layers × 512-d latent + kpool/indexer, fp8 ⇒ several KB/token ⇒ multiple GB per 1M request). [F] The EXL3 lane's pool is 1,243,902 fp8 tokens = "1.24×" a full 1M request; `MAX_NUM_SEQS=4` is the recipe's chosen default, not an engine-derived limit; at 262K the marlin lane reports 2.41× (512K) and the 4×Spark FP8 lane 15@200K / 5@500K / 3@1M. [F] vLLM has no per-request context cap distinct from `--max-model-len`; requests only consume blocks for tokens they actually hold, so "many short + one long" is permitted by allocation up to `max_num_seqs` — but if the pool fills, V1 preempts (recomputes) a running request, and a profiling guard ties `max_num_seqs` to "available Mamba cache blocks" (false-positive at >12 with MTP, #88). Levers: `--max-num-seqs`, `--kv-cache-dtype fp8` (already), `--mamba-ssm-cache-dtype bfloat16` (state size), `--kv-cache-memory-bytes` to pin the pool, `--mamba-cache-mode align` + `--prefix-match-unit` + retention interval for prefix reuse, `--long-prefill-token-threshold` for admission fairness.

**SGLang.** [F] Separate request-level Mamba pool (`--max-mamba-cache-size`, `--mamba-full-memory-ratio`) and token-level KV pool (`--max-total-tokens` or from `--mem-fraction-static`); `--max-running-requests` caps concurrency (and is reset to 48 under spec decode if unset); DFLASH needs `per_req×(1+D)` Mamba slots (one per draft token) — beastllama runs `--max-mamba-cache-size 40` for 8 running requests with D=8 plus "~5×" amplification; `--mamba-ssm-dtype bfloat16`; `--mamba-scheduler-strategy` V1 no_buffer (default, lower memory) vs V2 extra_buffer (overlap scheduling, more state memory). No per-request context knob separate from `--context-length` either, but because the Mamba pool is sized in *requests* while KV is sized in *tokens*, you can explicitly provision "N slots + a KV pool ≥ 1M + short-request headroom" rather than let the unified-page arithmetic decide [I]. Caveat: beastllama's 262K config died silently at ~62K prompts (32K passes) and their production config is 65K–131K, so SGLang's 1M viability on GB10 is unproven [F].

## Implications for our setup

**(a) Prefill throughput — invest in the vLLM EXL3 lane's kernel path and its batch size, not an engine switch (confidence: medium).** The engines are within ~1.5× of each other once the same FlashInfer-CUTLASS NVFP4 kernel is used; the 2× gaps in the community data come from Marlin vs CUTLASS vs FP8. Concretely: pull MiaAI PR77 (E2 fat-expert prefill, +20%); raise `--max-num-batched-tokens` from 7168 to 8192–16384 (the 4×Spark FP8 lane runs 8192–16384 with `FULL_AND_PIECEWISE` graphs) and re-measure prefill at 30K/100K — you are currently batching less than SGLang's 16384 default, which alone explains part of your 900 vs 1,800 gap; try `--moe-backend flashinfer_cutlass` on an NVFP4 checkpoint against EXL3 for prefill-only workloads (LibertAI: 1,283 at c1 with the `VLLM_GLM53_MOE_INPUT_SCALE=1.0` fix); watch the upstream `b12x`/`flashinfer_b12x` SM12x FP4 MoE backends, which are the first path that would use GB10's FP4 tensor cores rather than dequantising. On SGLang, raise `--chunked-prefill-size` to 8192–16384 for prefill throughput (at the cost of TTFT fairness) and add `--dsa-prefill-backend` alternatives only after verifying on sm_121 (fa4/trtllm unverified). Do not expect FP8-native GLM on 2 Sparks (306 GiB); that is the 4-Spark story (~2,100 tok/s).

**(b) TTFT under concurrency — vLLM with `--long-prefill-token-threshold` is the biggest single win; SGLang is the better scheduler for many medium prompts (confidence: high for the flag, medium for the engine call).** Issue #110 on your exact stack shows a 440 s freeze of concurrent sessions collapsing to 18–25 s with `--long-prefill-token-threshold 1024` (10.6% cost to the long prefill). Combine with `--max-num-batched-tokens ≥ 8192` so ≥2 chunks interleave, `--scheduling-policy priority` with gateway-assigned priorities (interactive > batch), and fix prefix-cache re-use for agent loops (`--prefix-match-unit` well below the 2304/3584 block, `VLLM_PREFIX_CACHE_RETENTION_INTERVAL` set to a multiple of the block, and pin `reasoning_effort` per session so #111 doesn't flush the cache). V1 cannot limit *how many* long prefills run concurrently, so put that admission control in your gateway. If your workload is dominated by 30K–150K prompts at c4–c12 with modest decode, SGLang's mixed-chunk + conservativeness knobs and token-level radix tree give finer control (c12 aggregate 83.5 vs vLLM's 53.3 in beastllama's comparison) — but only at ≤131K context on GB10 today.

**(c) Decode with spec decode — keep vLLM EXL3 + DFlash2 for c≤4, taper k with batch (confidence: high).** It is the fastest measured GLM-5.3-Flash decode on 2 Sparks (62.9 c1 / 146.5 agg ×4) and 2× SGLang's DFlash2. Add `num_speculative_tokens_per_batch_size` (e.g. k=7 for 1–2, 4 for 3–4, 2 or off ≥6) because on GB10 spec decode goes negative around c6–8; keep `FLASH_ATTN` for the drafter (Triton collapses late-position acceptance); expect prose at ~27 tok/s regardless (accept 0.34) — that is an acceptance problem, not a kernel one, and would need a GLM-specific DFlash2 retrain on your prose distribution. For DeepSeek-V4-Flash, move from MTP-2 to DSpark k=5 with probabilistic draft sampling (hazyumps/tonyd2wild: 47–84 vs ~41 tok/s) and turn on `enable_adaptive_verification`. On SGLang, if you stay there for prefill, use adaptive NEXTN (5/1/6) rather than DFLASH for c≥6, since DFLASH also disables the overlap scheduler.

**Concurrency at 1M (confidence: medium).** The 4-sequence cap is the recipe's `MAX_NUM_SEQS`, not a state-pool limit; raise it to 8–12 (not >12 with MTP until #88's `is_profiling` backport is in your image) and pin `--kv-cache-memory-bytes`. Because vLLM allocates blocks per actual tokens, many short/medium requests will coexist with one 1M request; the risk is preemption when the pool fills, so cap per-request `max_tokens`/prompt length in the gateway rather than in the engine, and reserve headroom (pool ≥ 1.24M tokens already gives you ~240K tokens of "short-request" room beside one 1M session). Set `--mamba-ssm-cache-dtype bfloat16` if the state is still fp32 in your build to shave the per-request page cost.
