# GLM-5.3-Flash: architecture, engine internals, and prefill cost model

Scope note: everything marked **[F]** is a fact traced to a cited primary source (config.json, transformers/vLLM/SGLang source, papers, engine docs, community repos); **[I]** is my inference/derivation. One correction to the premise: the model is **320B total / 18B active**, not ~30B active [F: [model card](https://huggingface.co/zai-org/GLM-5.3-Flash), [docs.z.ai](https://docs.z.ai/guides/vlm/glm-5.3-flash)]; my parameter reconstruction below reproduces 321B / 17.4B.

## 1. Exact architecture

**Provenance.** There is no separate GLM-5.3-Flash paper; the card points to the GLM-5 report ([arXiv 2602.15763](https://arxiv.org/abs/2602.15763)), which documents the 744B-A40B GLM-5 (80 layers, 256 experts, DSA, MTP accept length 2.76) but nothing about the Flash variant [F]. The authoritative Flash sources are `config.json`, the safetensors index, and the transformers `modeling_glm5_next.py` (all read directly). Released 2026-08-26, MIT, 30T-token multimodal corpus, 1M context, 128K max output; Z.ai claims 3.01x less attention compute and 4.44x less KV cache than text GLM-5.3 (92 layers) [F: docs.z.ai].

**config.json (text_config) — key fields** [F: [config.json](https://huggingface.co/zai-org/GLM-5.3-Flash/raw/main/config.json)]:
`model_type glm5_next_text`, `architectures Glm5NextForConditionalGeneration`, `num_hidden_layers 45`, `hidden_size 4096`, `layer_types`: 34 `linear_attention` + 11 `deepseek_sparse_attention` at indices **3,7,11,…,43** (3:1 pattern, KDA at 0–2 and a trailing KDA at 44), `indexer_types` all `"full"` (no cross-layer index sharing in this release), `mlp_layer_types`: 3 dense (`first_k_dense_replace 3`) + 42 sparse, `intermediate_size 12288` (dense), `moe_intermediate_size 2048`, `n_routed_experts 288`, `num_experts_per_tok 8`, `n_shared_experts 1`, `scoring_func sigmoid`, `topk_method noaux_tc`, `n_group 1`, `topk_group 1`, `norm_topk_prob true`, `routed_scaling_factor 2.5`, `moe_router_dtype float32`, `swiglu_limit 10.0`, `linear_attn_config {num_heads 64, head_dim 128, short_conv_kernel_size 4, gate_lower_bound -5.0}`, `num_attention_heads 64`, `q_lora_rank 1536`, `kv_lora_rank 512`, `qk_nope_head_dim 256`, `qk_rope_head_dim 0`, `v_head_dim 256`, `mla_use_nope true`, `index_n_heads 32`, `index_head_dim 128`, `index_topk 2048`, `index_kpool 4`, `index_kpool_compress true`, `index_kpool_always_select_tail true`, `index_share_for_mtp_iteration true`, `indexer_rope_interleave true`, `mhc true`, `hc_mult 4`, `hc_sinkhorn_iters 20`, `hc_eps 1e-6`, `num_nextn_predict_layers 1`, `vocab_size 154880`, `max_position_embeddings 1048576`, `tie_word_embeddings false`. `quantization_config`: `fp8`, `e4m3`, `weight_block_size [128,128]`, `activation_scheme dynamic` — the default checkpoint is **FP8 W8A8**; a `GLM-5.3-Flash-BF16` variant exists [F: [vLLM recipe](https://recipes.vllm.ai/zai-org/GLM-5.3-Flash)]. Vision: 24-block ViT, hidden 1024, patch 14, merge 2, out 4096.

**KDA (Kimi Delta Attention)** [F: transformers source; [Kimi Linear paper](https://arxiv.org/html/2510.26692)]. 64 heads x 128 (d_k = d_v = 128; note Kimi Linear used 16 heads — GLM quadruples the head count). Pipeline: `q_proj/k_proj/v_proj` (4096->8192 each) -> per-projection depthwise causal conv1d (kernel 4, SiLU) -> QK L2-norm in-kernel -> gated delta rule with **per-channel** decay. Forget gate: `g = f_b(f_a(x)) + dt_bias` (low rank 4096->128->8192), decay = `gate_lower_bound * sigmoid(exp(A_log) * g)` = `-5 * sigmoid(...)` (the "safe gate" branch, since `gate_lower_bound=-5.0`); `beta = sigmoid(b_proj(x))` (per head); output gate `g_b(g_a(x))` low-rank, applied in a gated RMSNorm before `o_proj`. Recurrence: S_t = (I − β_t k_t k_tᵀ) Diag(α_t) S_{t−1} + β_t k_t v_tᵀ. Chunk kernel `chunk_kda` uses chunk size **64** (asserts 32 or 64, K<=256); decode uses `fused_recurrent_kda`; complexity per token O(d² + C·d + C²) — linear in T [F: fla `ops/kda/chunk.py`, Kimi paper]. **State per sequence**: 64 x 128 x 128 fp32 = 4 MiB/layer -> **136 MiB for 34 layers** (68 MiB/rank at TP=2, heads sharded) plus ~150 KB conv state/layer [I]. KV cache per token for the 11 MLA layers: 512-d latent (no RoPE part) = 11.3 KB bf16 / 5.6 KB fp8, plus pooled indexer keys 128 B fp8 per 4 tokens per layer [I]; community measurement: 512 B/token fp8, 368 B/token NVFP4-KV [F: [tonyd2wild 4x](https://github.com/tonyd2wild/GLM-5.3-Flash-NVFP4-1M-KV-4x-DGX-Spark)].

**Sparse MLA + KPool indexer** [F: transformers `Glm5NextTextAttention`, `Glm5NextTextIndexer`]. MLA is DeepSeek-style with **no RoPE anywhere in the main path** (`qk_rope_head_dim=0`, so `kv_a_proj_with_mqa` is 4096->512 only); 64 heads, q_lora 1536, nope head dim 256, v 256; hence the latent-cache attention is MQA over a 512-d shared K/V. Indexer per layer: `wq_b` (1536->32x128), `wk` (4096->128) + LayerNorm, `weights_proj` (4096->32), `index_kpool_compress_gate` (128x4096) and `index_kpool_compress_ape` (4x128). Every 4 consecutive keys are compressed into one **pooled key** by a per-channel softmax over the 4 slots with logits `gate(x) + ape` (learned, not mean-pooling). Score per pool: I[t,p] = Σ_h w[t,h]·ReLU(q[t,h]·k_p)·d^{-1/2}·H^{-1/2}. Top-k is taken over **pools** with `select_k = index_topk / index_kpool = 512` pools -> 2048 raw token indices, then the current incomplete tail pool (≤3 tokens) is always appended (`always_select_tail`), so the attended set is ≤2051 tokens. When context ≤2048, engines skip the indexer and do exact attention (`_fill_causal_indices` / `_full_topk_for_short_sequence`) [F: vLLM `sparse_attn_indexer_kpool.py`, SGLang `dsa_indexer_kpool.py`]. The indexer itself uses RoPE (`indexer_rope_interleave`) and runs in FP8 with a Hadamard-128 transform on q/k in the engines. Cost: scoring is **quadratic in context** — per query, 32x128 MACs per pool over L/4 pools (1/4 the cost of DeepSeek's DSA indexer; GLM-5.2 already noted the indexer as the quadratic remnant [F: [Raschka, GLM-5.2 IndexShare](https://sebastianraschka.com/blog/2026/glm-5-2-indexshare.html)]); the main attention is O(L·2048), i.e. constant per token beyond 2K.

**MoE** [F: transformers `Glm5NextTextTopkRouter`, `Glm5NextTextExperts`]. Router: `scores = sigmoid(x·W_g)` in fp32; selection uses `scores + e_score_correction_bias` (DeepSeek-V3 "noaux_tc"); with `n_group=topk_group=1` the grouping is a no-op; weights are the **un-biased** sigmoid scores of the top-8, renormalized to sum 1 (`norm_topk_prob`), then multiplied by `routed_scaling_factor=2.5`. One shared expert (same 4096x2048 SwiGLU shape) added unconditionally. `swiglu_limit`: `gate = clamp(gate, max=10)`, `up = clamp(up, -10, 10)` **before** SiLU (gpt-oss-style clamp), applied in dense MLPs, experts, and the vision MLP.

**mHC (Manifold-Constrained Hyper-Connections)** [F: [arXiv 2512.24880](https://arxiv.org/html/2512.24880v2); transformers `Glm5NextTextHyperConnection`]. The residual stream is widened to n=4 parallel 4096-d streams. Per sublayer (2 per layer, 90 total): flatten streams to 16384, unweighted RMSNorm, GEMM with `hc_fn` (24 x 16384) -> 4 "pre" logits, 4 "post" logits, 16 "comb" logits, each scaled/biased by `hc_scale`/`hc_base`; `pre = sigmoid(·)+eps` collapses the 4 streams into the sublayer input; `post = 2·sigmoid(·)` places the sublayer output back into each stream; `comb` is Sinkhorn-projected (20 iterations of row/column normalization) to a doubly-stochastic 4x4 mixer: `streams_out = combᵀ·streams + post ⊗ f(x)`. Final head is an unweighted mean of the 4 streams. The MTP layer has **no** hc tensors [F: safetensors index, layer 45]. FLOPs are negligible (~0.09 GFLOP/token); the cost is **memory traffic on a 4x-wide residual** — the paper counts (5n+1)C reads + (3n+1)C writes per token per sublayer unfused and reports 6.7% training overhead only after TileLang kernel fusion.

**MTP.** One NextN layer (`layers.45`): `enorm`, `hnorm`, `eh_proj` (8192->4096), a **DSA/MLA block with its own indexer, a full MoE block**, `shared_head.norm`; ~7.4B params, 0.23B active per draft step [F: safetensors index; vLLM `mtp.py`]. `index_share_for_mtp_iteration` (reuse the first draft step's top-k) is in config but unimplemented in llama.cpp's MTP PR [F: [#27917](https://github.com/ggml-org/llama.cpp/pull/27917)]. Reported acceptance: MTP-4/5 ≈ 2.5 accept length on 2x Spark [F: [NVIDIA forum](https://forums.developer.nvidia.com/t/glm-5-3-flash-running-on-2x-dgx-spark-sm-121-day-0-24-7-30-3-tok-s-with-mtp-5-two-silent-gb10-gotchas-worth-knowing/381433)]; llama.cpp MTP 0.745 per-token, mean length 4.13 [F: #27917]; DFlash2 (1B block-diffusion drafter, `incoai/GLM-5.3-Flash-DFlash2`, **CC BY-NC-ND**) 74% at k=7 on Spark, 0.94–0.98 per position on structured output [F: [tonyd2wild](https://github.com/tonyd2wild/GLM-5.3-Flash-NVFP4-DFlash2-2x-DGX-Spark), [MiaAI-Lab](https://github.com/MiaAI-Lab/GLM-5.3-Flash-EXL3-2x-DGX-Sparks)]. Tokenizer: 154,880 vocab, eos ids 154820/154827/154829.

**Official FP8 checkpoint precision map** [F: `modules_to_not_convert` + presence of `weight_scale_inv`]: FP8 block-128 = all routed/shared experts, dense MLPs, MLA `q_a/q_b/kv_a/o_proj`. Kept BF16 = **all KDA projections** (`q/k/v/o_proj`, gates, conv), `kv_b_proj`, indexer, mHC, router (+bias), embeddings, lm_head, vision.

## 2. Engine implementations (vLLM, SGLang)

Neither engine has Flash support on `main` as of today: vLLM [PR #53906](https://github.com/vllm-project/vllm/pull/53906) (open, +17.9k lines, branch `glm-release`) and SGLang [PR #36507](https://github.com/sgl-project/sglang/pull/36507) (open); shipped via `vllm/vllm-openai:glm53-flash*` and `lmsysorg/sglang:glm-5.3-flash` images [F].

## 4. Prefill cost model for this architecture (TP=2, 8,192-token chunk)

GB10 measured peaks: 99.8 TFLOPS BF16, 207.7 TFLOPS FP8 dense, 273 GB/s [F: [LMSYS Spark review](https://www.lmsys.org/blog/2025-10-13-nvidia-dgx-spark/)]. FLOPs are per token (2 x MACs), chunk-level weight bytes are per rank [I, derived from the shapes above]:

| Component | GFLOP/token | Scaling in L | Weight bytes/chunk/rank (4-bit experts, BF16 rest) | Notes |
|---|---|---|---|---|
| Routed experts (42 x 8 x 25.2M) | **16.9** | linear | **~78 GB** (EXL3 4.05 bpw); 81 GB NVFP4; 153 GB FP8 | 8192x8/288 ≈ 228 rows per expert per chunk; TP=2 halves N to 1024 (gate/up) |
| Shared expert (42) | 2.1 | linear | 3.7 GB incl. above | dense GEMM, M=8192 |
| Router (42 x 4096x288) | 0.1 | linear | 0.05 GB | fp32 sigmoid + bias top-k |
| Dense MLP (3) | 0.9 | linear | 0.12 GB | |
| KDA projections + gates (34) | 9.1 + 0.25 | linear | 4.7 GB | BF16 in official ckpt |
| KDA core (chunk 64) | ~0.25 | linear | scratch only (#54775) | Triton; profile shows 6% -> ~10x its FLOP share |
| MLA projections (11) | 2.6 | linear | 1.3 GB | kv_b expands 512->32768 per token |
| Sparse attention core (11) | 1.5 (materialized K/V) – 5.9 (absorbed MQA over 512-latent) | **constant for L ≥ 2048** | KV reads ≤ 2051 x 512 B x 64 heads | |
| Indexer projections (11) | 0.15 | linear | 0.16 GB, replicated on both ranks | |
| Indexer scoring + top-k (11) | 0.09 @8K, 0.37 @32K, 1.5 @128K, **11.9 @1M** | **quadratic total** (≈11,264·L FLOP/token avg) | pooled fp8 keys: 32 B/token/layer | top-k over L/4 pools |
| mHC (90 sublayers) | 0.09 | linear | 0.07 GB | activation traffic ≥ 5.8 MB/token fused, ~25 MB/token unfused (paper's count) |
| lm_head / MTP layer prefill | ~0 / +0.5 | — | 0.63 GB / +1.9 GB | MTP layer must be prefilled to fill its KV |
| **Total** | **~33–38 GFLOP/token** | | **~86 GB/rank/chunk** | |

What this says [I]:
- Compute floor for an 8K chunk: 8192 x 35 GFLOP ≈ 290 TFLOP / (2 x 100 TFLOPS BF16) ≈ 1.45 s -> ~5,600 tok/s ceiling in BF16 tensor math, ~11,000 tok/s in FP8, higher in FP4. Weight-streaming floor: 86 GB / 273 GB/s ≈ 0.31 s -> ~26,000 tok/s. Measured 900–1,800 tok/s is 16–32% of the BF16 compute ceiling; prefill is **kernel-efficiency-bound, not bandwidth-bound**, and the MoE at 63% of 9.1 s/chunk (5.7 s for ~155 TFLOP) is running at ~27 TFLOPS effective ≈ 13% of the two GB10s' BF16 peak.
- Superlinear terms are only the indexer scoring/top-k (quadratic total; replicated on both TP ranks in vLLM) — negligible below 32K, equal to the KDA projections around 128K, and larger than the routed experts at 1M. Everything else is linear.
- mHC memory traffic is the hidden line item: 4x-wide residual, read/written twice per layer, 45 layers. Fused lower bound ≈ 5.8 MB/token -> 47 GB per 8K chunk per rank (0.17 s); the paper's unfused element count gives ~25 MB/token -> 205 GB (0.75 s at 273 GB/s), which would be **2.6x the expert-weight traffic** and roughly the unattributed ~10% of your profile.

## 5. Quantization behaviour

[F] Official: FP8 W8A8 (dynamic activation scales, block-128 weights) on experts, dense MLPs, MLA projections; KDA/indexer/mHC/kv_b/embeddings BF16. Indexer runs in FP8 by design (fp8 pooled keys + Hadamard). Community quality data (all on different eval sets — compare within a row's methodology only): EXL3 panel — BF16 floor 0.0115, TR3-K8 0.0124, K6 0.0137, **4.05 bpw 0.0255 (top-1 0.951)**, 3.0 bpw 0.0505, 2.0 bpw 0.155 [F: [turboderp discussion](https://huggingface.co/turboderp/GLM-5.3-Flash-exl3/discussions/1)]; brandonmusic TR3 4 bpw KLD 0.0246 with FP8 KV, 0.0548 with NVFP4 KV [F]; ModelOpt NVFP4 (local-inference-lab) "KLD ~0.04", LibertAI per-expert cosine 0.9967 [F]; Unsloth GGUF Q4_K_XL mean KLD 0.049, IQ3_XXS 0.284, IQ1_S 0.670 [F: [unsloth docs](https://unsloth.ai/docs/models/glm-5.3-flash)]; RedHatAI W4A4 NVFP4 reports GPQA-D 90.6 / AIME25 86.7 / MATH-500 94.9 with no baseline [F]. Activation quantization in deployment: FP8 activations (official), **FP4 activations** (RedHatAI compressed-tensors W4A4; the format used by the corruption-free Spark recipes), W4A16 (ModelOpt weight-only, AWQ), MXFP4 W4A4 megamoe (SGLang flag), NVFP4 KV-cache experiments (KLD doubles) [F]. [I] EXL3 4 bpw is currently the best-quality 4-bit expert format by KLD (~0.025 vs ~0.04–0.05), but it is weight-only (BF16 activations, dequant-in-kernel), which is exactly why its prefill trails NVFP4 W4A4 tensor-core GEMMs.

## Implications for our setup (2x GB10, TP=2, EXL3 in vLLM fork / NVFP4 in SGLang)

Ordered by expected prefill payoff; confidence in brackets.

1. **Expert GEMM kernel efficiency (63%, running at ~13% of BF16 peak) — [high].** The MoE is neither weight-bandwidth-bound (0.3 s/chunk floor) nor FLOP-bound (1.45 s floor) at 9 s/chunk. Three concrete levers, in order: (a) for prefill-sized M (~228 rows/expert), dequantize each EXL3 expert tile once to BF16/FP8 in shared memory and run a real tensor-core grouped GEMM, rather than trellis-decoding inside the inner loop — MiaAI's "E2 fat-kernel" restructuring alone gave +20% on identical hardware; (b) consider **EP=2 instead of TP=2 for the experts**: TP halves N to 1024 for gate/up and K to 1024 for down, giving skinny per-rank GEMMs; EP keeps full 2048-wide expert shapes with 144 experts/rank and swaps the two allreduces per layer for one all-to-all (the RTX PRO 6000 result uses TP2+EP2) [medium]; (c) the SGLang NVFP4 2x gap is mostly FP4 tensor-core activations (W4A4) — if quality budget allows, an FP8-activation path for the EXL3 kernel (dequant 4-bit -> FP8, FP8 GEMM at 207 TFLOPS) is the natural middle ground [medium].
2. **mHC implementation — [medium, cheap to verify].** Check whether the fork hits `mhc_pre_tilelang`/`mhc_post_tilelang` or the torch fallback on sm_121 (TileLang is frequently not built for sm_121). If unfused, the 4-wide residual traffic (~25 MB/token) is on the order of the expert-weight traffic and plausibly the unattributed ~10% of the profile; a fused pre (RMSNorm + 24x16384 GEMM + Sinkhorn + collapse) and fused post (combᵀ·streams + post⊗out) kernel bounds it at ~6 MB/token. Also fuse `input_layernorm` into the collapse.
3. **Allreduce (7%) — [medium].** 90 allreduces of 64 MB per 8K chunk ≈ 5.8 GB per rank; at 25 GB/s wire that is ~0.23 s ≈ 2.5%, so 7% implies ~10 GB/s effective. Verify NCCL is on the RoCE HCA with `NCCL_IB_HCA`/`NCCL_IB_GID_INDEX` set (community launchers needed explicit env), and use larger `max-num-batched-tokens` to amortize per-collective latency. EP would also reduce this to one all-to-all per MoE layer.
4. **KDA (6% for ~0.7% of FLOPs) — [medium].** The Triton chunk kernel is memory- and launch-bound; the vendored vLLM kernel autotunes chunk 32/64/128, and SGLang exposes cutedsl/flashkda/helion dispatchers worth benchmarking on sm_121. Also watch [#54775](https://github.com/vllm-project/vllm/issues/54775): chunked-scan scratch (~3.75 GiB/layer at 80K batched tokens) is outside memory profiling; keep `max-num-batched-tokens` sized with that in mind.
5. **Sparse attention + indexer (4%) — leave alone below ~64K [high].** Constant-cost attention over ≤2051 tokens; indexer cost is quadratic but only reaches parity with the KDA projections around 128K context, and it is replicated on both ranks (the sharding PR #54951 is unmerged) — relevant only if you routinely prefill >100K. Do apply the sm_121 `persistent_topk` initialization patch (decode crash >24K) and the kpool-tail slot-map fix.
6. **Decode is a different regime [high].** At ~18B active x 4 bits ≈ 9 GB/token/rank at batch 1, decode is bandwidth-bound (~14–15 tok/s no-spec on this box in every report); the only large lever is speculation depth (DFlash2 k=7: 47–63 tok/s vs MTP-4/5: 22–30). Note the DFlash2 drafter's CC BY-NC-ND license if this is commercial. Prefix caching for the hybrid state is coarse (3584-token page alignment in the EXL3 fork; vLLM align-mode caching can silently be 0%) — worth verifying hit rates before relying on it for agentic multi-turn.

Quality stance: EXL3 4.05 bpw (KLD ≈ 0.025) is the better-quality choice versus NVFP4 W4A4 (≈ 0.04 + FP4-activation error, whose effect is not independently measured); if you move activations to FP8 to buy prefill, that is closer to the official FP8 W8A8 deployment than W4A4 is [I].
